# 数学問題解決用テンプレート構築計画

## 目的

`templates/` を `cp -r path_to/templates/* project/` のように問題ごとの作業ディレクトリへ複製して使い、未解決問題級の数学問題を再帰的自己改善の考え方で検討できる作業環境を整える。複製先で問題を解き、個別問題の成果物は複製先に作成する。

テンプレートには、問題解決ワークフローを記した `AGENTS.md` と、Dockerfileなど起動に必要な構成を含むPython・uv・FastMCPによる `workflow_mcp` を含める。ワークフローの進行は `AGENTS.md` が担い、MCPはコーディングエージェントの権限では行えない操作を担う。問題解決の各工程に対応する方針ファイルはテンプレートに含めず、コピー先の反復で形成する。

テンプレートは完成済みの数学方針や方針ファイルを問題ごとに配るものではない。コピー先で `AGENTS.md` に従ってRSIの反復を行い、その過程で工程に対応する方針を形成し、フィードバックを参照して必要な方針を作成・見直し、次のループで用いる作業環境を提供する。

## 背景

RSI-Anythingを参考にするのは、方策で候補を出し、ワールドモデルによるシミュレーションで候補の展開を予想し、その後に得られる実際のフィードバックを次の改善に使う循環である。予想や成果を記録して次のターンへ渡すだけではなく、経験から有意義な学びを選び、次の方針を作る際に参照して、後続の検討の進め方を変える。

数学問題では、方策が直接の解法に限らない数学的アイデアを出し、シミュレーションがそのアイデアを進めると何が言えそうか、どのような展開や難点がありそうかを短い範囲で自然言語により予想する。評価を通じて有望な候補を選び、その方向を実際に深掘りする。実際の検討結果をシミュレーションの予想や候補選択と照らし合わせ、目標達成、行き詰まり、予想からの大きな乖離などを手がかりに、次の方針を作るうえで有意義な学びがあるかを判断する。

方針ファイルはテンプレートから配布する完成品ではなく、各工程に対応する形でコピー先の反復の中で形成される。各方針の具体的な内容、シミュレーションで何をどう記録するか、有意義なフィードバックの具体的な内容はあらかじめ固定しない。これは設計上の未決ではなく、反復の経験に基づいて方針を形成するための前提である。フィードバックは方針ファイルに直接書き込まず、次ターンへ渡す別の記録として保持する。次のコーディングエージェントは、該当する方針を作成・見直す際に有効なフィードバックを参照し、その内容をどう生かすか考える。方針を毎回すべて変更する工程や、独立した承認工程は設けない。

この計画で変化するのは、コピー先の反復で形成される各工程の方針と、経験から有意義なフィードバックを選び次の方針形成に用いる方法である。コーディングエージェントの基盤モデル自体を変更するものではない。

## 複製利用の前提

このリポジトリでは、再利用する仕組みを `templates/` に用意し、数学問題ごとにその内容を作業ディレクトリへコピーして使う。想定例は `cp -r path_to/templates/* project/` である。問題の検討、方針の形成、rolloutやフィードバックなど個別問題に属する成果物は、コピー元の `templates/` ではなくコピー先のプロジェクトに作成する。

この使い方では、テンプレート内の構成をコピー先から利用できる必要がある。たとえば `templates/dev_mcp/workflow_mcp/` はコピー後に `project/dev_mcp/workflow_mcp/` となるため、Docker関連の設定や起動時の参照先はこの配置で機能するようにする。既存のdev_mcp資料は構成の参考にするが、資料中の版番号、ポート、環境変数などをそのまま確定値とはしない。

想定例の `*` は通常、隠しファイルを対象にしない。したがって、必要な隠しファイルの配置やコピー方法は実装時の検討事項として残す。このコピー・利用の前提は各実施段階に反映する条件であり、独立した作業段階ではない。

## 中核ワークフロー

コピー先で形成する方針を、対応する工程の成果を生成するために使う。成果はコピー先に記録し、次の工程または次のループで使う。

工程の順序は、方策、シミュレーション、評価・選択、実行、フィードバック、次の方策とする。

1. **方策**: 4つの方針ファイルをまとめた方策候補を作る。前のターンに有効なフィードバックがあれば、関係する方針を作成・見直す際に参照する。
2. **シミュレーション**: `simulation_policy.md` に従って、各方策候補で数学的な検討を進めた場合の展開を予想・短期検討する。
3. **評価・選択**: `evaluation_policy.md` に従ってシミュレーション結果を評価し、実行する方策候補を選ぶ。
4. **実行**: 選んだ方策の `solution_policy.md` に従って、実際の数学的検討を進める。実行中にも `evaluation_policy.md` に従って評価し、検討を続けるかフィードバックへ進むか判断する。
5. **フィードバック**: `feedback_policy.md` に従って、実行結果から次のループに有意義なフィードバックを生成・選別し、次の方策へ渡す。

### 各方針ファイルに期待する内容

4つのファイルはいずれも方策工程で生成する。具体的な方針の内容は、有効なフィードバックを参照して反復の中で形成する。

**`simulation_policy.md`**

シミュレーション工程で、各方策候補に従って検討した場合の展開を予想・短期検討するための方針を記す。当面は計算機を使わず、「こういうことが言えるかもしれない」「この方向は難しそう」「可能性がありそう」といった見通しを自然言語で検討する。何をどう記録するかもこの方針で選び、出力の形式やファイル粒度をあらかじめ固定しない。

**`evaluation_policy.md`**

評価・選択と実行中の評価で使う方針を記す。シミュレーションの予想をどう評価し、どの方策候補を実行するか選ぶための判断を導く。また、実際の検討結果を予想と照らし、検討を続けるか、目標達成・行き詰まり・予想からの大きな乖離などを区切りにフィードバックへ移るかを判断する。予想することや数学的に検討することと、それらを評価することは別の役割として扱う。

**`solution_policy.md`**

実行工程で数学的な検討を進めるための方針を記す。どのような数学的アイデアや方向を試し、どう深掘りするかを導く。直接の解法に限らず、解決に間接的に役立つ可能性のある方向も扱う。実行で得た検討結果は、この方針に従って作る別の記録として残す。

**`feedback_policy.md`**

フィードバック工程で、実行の成果、行き詰まり、予想との乖離から、次のループに有意義な内容を生成・選別するための方針を記す。数学的な検討の進め方だけでなく、シミュレーションや記録方法、評価、フィードバックの作り方自体に関する学びも対象となる。毎回すべての方針にフィードバックを作る必要はない。選別した内容は別のフィードバック記録に残し、次の方策で関係する方針を作成・見直す際に参照する。

## 工程を支える説明

### シミュレーションと記録方法

当面のシミュレーションでは計算機を使わず、自然言語で可能性や難点を予想する。何をどう記録するかも `simulation_policy.md` の対象とし、個々の出力を1ファイルに固定しない。

### 評価とフィードバックの区切り

`evaluation_policy.md` は、評価・選択と実行中の評価の両方で使う。

目標達成、行き詰まり、予想からの大きな乖離などをフィードバックへ移る区切りとする。成果、行き詰まり、予想との乖離を整理し、次のループへ渡す価値があるかを判断する。毎回すべての要素にフィードバックを作る必要はない。フィードバックの内容上の種類と、どの方針に関係するかは別の軸である。

### フィードバックの保持とMCPの役割

- 有効なフィードバックは該当ディレクトリの `README.md` で分かるようにし、次ターンに渡す。
- コピー先のエージェントは、該当する方針を作成・見直す際に引き継いだ有意義なフィードバックを参照し、その内容をどう生かすか考える。
- 却下するフィードバックは削除せず、`rejected_feedbacks` に保持する。通常のエージェントが読書きできないようにする方向で設計する。
- フィードバックのrejectは、対象ターンを指定するMCP操作として実装する方向とする。
- `workflow_mcp` は、権限制約のためコーディングエージェント自身では実行できない操作を担う。拒否済みフィードバックを退避する操作が最初の対象候補である。
- フィードバックの分類と、rolloutを表示・非表示にする判断は混同しない。

## 実施計画

### 1. 問題解決用テンプレートの作成

- `templates/AGENTS.md` に反復工程と、コピー先で工程に対応する方針を形成し、フィードバックを参照して必要な方針を作成・見直し、次のループで用いる流れを記す。
- 方針ファイルは `templates/` に置かず、コピー先の反復で形成する。
- 問題ごとの成果物をテンプレートの説明文書へ混在させず、複製先で作成する。
- 個別の数学的候補・rollout・実際の検討結果・フィードバックの記録は、コピー先で方針に基づいて選択・形成できるようにする。
- 指定された `cp -r path_to/templates/* project/` で必要なファイルが複製され、コピー先から各構成を使えるようにする。

成果物: 方針形成を含むRSIの反復をコピー先で始められる `AGENTS.md` と方針の枠組み。

### 2. workflow_mcpの設計と実装

- 実装本体を `templates/dev_mcp/workflow_mcp/` に置く。
- 実装言語・主要ライブラリはPython、uv、FastMCPとする。
- 担当するのはエージェントの権限で実行できない操作に限る。ワークフローの判断や工程進行は担当させない。
- まずreject対象の指定方法、`rejected_feedbacks` への退避、エージェントからのアクセス制限を設計して実装する。
- Docker Compose、Dockerfile、uvの依存関係、起動スクリプトは既存のdev_mcp手順を参考にし、`cp` 後の `project/dev_mcp/workflow_mcp/` から正しく参照できるようにする。
- `cp -r path_to/templates/* project/` で必要な隠しファイルが欠落しない方法を、テンプレートのファイル配置と合わせて定める。

参考: `docs/手順/centers/docker-center/docker-center対応方法.md` の「dev_mcp（開発用MCP）の例」。同資料の版番号、ポート、環境変数などは例示値として扱う。

成果物: 複製可能な `workflow_mcp` と起動に必要な構成。

## 実装時に決める事項

- `workflow_mcp` のツールAPIと、対象ターンを使ったreject対象の指定方法。
- `workflow_mcp` が `rejected_feedbacks` へ書き込める構成と、通常のエージェントからのアクセスを分ける方法。既存dev_mcpの読み取り専用マウントとの整合も確認する。
- 指定されたコピー方法で必要なファイルを欠落させないための配置。
- Python版、Dockerベースイメージ、ポート、キャッシュ配置などの採用値。

## 完了条件

- 指定された `cp -r path_to/templates/* project/` で `templates/` を問題ごとに複製し、複製先でワークフローを開始できる。
- `AGENTS.md` が、方針をコピー先のRSI反復過程で形成し、フィードバックを次のループへ持ち越す流れを示している。
- テンプレートは問題用 `AGENTS.md` とMCP関連の構成を提供し、方針ファイルはコピー先の反復で形成される。
- 自然言語の短期シミュレーション、候補選択、深掘り、結果評価、選別フィードバックの流れが `AGENTS.md` で追える。
- 有効フィードバックをREADMEで次ターンへ渡せ、却下分はMCP経由で通常のエージェントアクセス範囲から分けて保存できる。
- `workflow_mcp` は権限外操作を担い、ワークフロー自体を進行しない。
- Docker、Python、uv、FastMCPの構成と複製後のパスが一致している。
