# workflow_mcp構想

## 目的

このリポジトリでは、再帰的自己改善（RSI）の方法で数学問題を解くための、再利用可能な作業雛形を保守する。雛形を問題ごとの作業ディレクトリに複製し、そのコピー先で問題を解く。個別問題の解答はコピー先に作成する。

## 配置と利用の流れ

- `workflow_mcp` は開発用MCPとして作る。
- 再利用するテンプレートは `templates/dev_mcp/workflow_mcp/` に置く。
- 問題ごとのプロジェクトは、テンプレートディレクトリの内容をコピーして作る。例: `cp -r path_to/templates/* project/`
- コピー後は `project/dev_mcp/workflow_mcp/` にMCPが配置される。
- 雛形にはDockerfile、Python・uv・FastMCPによるMCPツール、問題解決用 `AGENTS.md` などを含める。具体的なMCPの機能とファイル配置は設計で決める。
- 上記の `*` はシェルの通常のパス名展開ではドットファイルに一致しない。実際の複製手順では `.env.example` や `.python-version` などの隠しファイルも含める方法を決める。

## 数学問題を解くループ

- ワークフロー自体は問題解決用 `AGENTS.md` に記述する。
- 工程の順序は、方策、シミュレーション、評価・選択、実行、フィードバック、次の方策とする。
  1. **方策**: 4つの方針ファイルをまとめた方策候補を作る。有効なフィードバックは、関係する方針を作成・見直す際に参照する。
  2. **シミュレーション**: `simulation_policy.md` に従って、各方策候補で数学的な検討を進めた場合の展開を予想・短期検討する。当面は計算機を使わず、自然言語で行う。
  3. **評価・選択**: `evaluation_policy.md` に従ってシミュレーション結果を評価し、実行する方策候補を選ぶ。
  4. **実行**: 選んだ方策の `solution_policy.md` に従って数学的な検討を進める。実行中にも `evaluation_policy.md` に従って評価し、検討を続けるかフィードバックへ進むか判断する。
  5. **フィードバック**: `feedback_policy.md` に従って実行結果から有意義な内容を生成・選別し、次の方策へ渡す。特に有効なフィードバックは該当ディレクトリの `README.md` に示す。別個の方針改訂・採用ゲートは設けない。
- 各工程の成果物は、その工程に対応する方針に従って生成・記録し、後続工程が前工程の記録を入力として使う。具体的な配置、個別成果物の粒度、ファイル形式は未確定。

## 方針の構成

- 方針は単一ファイルではなく、役割別の方針ファイルをまとめるディレクトリにする。
- 4つの方針ファイルはいずれも方策工程で生成する。`<用途>_policy.md` という名前は、その方針を入力として使う工程を示す。

具体的な方針の内容は、有効なフィードバックを参照して反復の中で形成する。

**`simulation_policy.md`**

シミュレーション工程で、各方策候補に従って検討した場合の展開を予想・短期検討するための方針を記す。当面は計算機を使わず、「こういうことが言えるかもしれない」「この方向は難しそう」「可能性がありそう」といった見通しを自然言語で検討する。何をどう記録するかもこの方針で選び、出力の形式やファイル粒度をあらかじめ固定しない。

**`evaluation_policy.md`**

評価・選択と実行中の評価で使う方針を記す。シミュレーションの予想をどう評価し、どの方策候補を実行するか選ぶための判断を導く。また、実際の検討結果を予想と照らし、検討を続けるか、目標達成・行き詰まり・予想からの大きな乖離などを区切りにフィードバックへ移るかを判断する。予想することや数学的に検討することと、それらを評価することは別の役割として扱う。

**`solution_policy.md`**

実行工程で数学的な検討を進めるための方針を記す。どのような数学的アイデアや方向を試し、どう深掘りするかを導く。直接の解法に限らず、解決に間接的に役立つ可能性のある方向も扱う。実行で得た検討結果は、この方針に従って作る別の記録として残す。

**`feedback_policy.md`**

フィードバック工程で、実行の成果、行き詰まり、予想との乖離から、次のループに有意義な内容を生成・選別するための方針を記す。数学的な検討の進め方だけでなく、シミュレーションや記録方法、評価、フィードバックの作り方自体に関する学びも対象となる。毎回すべての方針にフィードバックを作る必要はない。選別した内容は別のフィードバック記録に残し、次の方策で関係する方針を作成・見直す際に参照する。

- フィードバックの内容上の種類と、どの方針を更新対象にするかは別の論点である。種類分けや、個々のフィードバックと方針の対応づけは未決定。
- 方針ファイルが個々の数学的アイデアやシミュレーション記録をどのように参照・保持するか、また各成果物をどの単位でファイル化するかは未決定。
- RSIの再帰性は、有効なフィードバックを次ターンのコーディングエージェントに渡し、そのターンの作業で必要な方針へ反映することで、次ループの行動を変える点にある。別個の方針改訂・採用ゲートは設けず、具体的な改訂作業は問題解決用 `AGENTS.md` に従って行う。

## workflow_mcpの役割

- ワークフローの指示・進行は問題解決用 `AGENTS.md` が担う。
- `workflow_mcp` はワークフロー全体を管理するものではなく、コーディングエージェントの権限では実行できない操作を担う。
- その操作の具体的な範囲やツール仕様は未確定。

## フィードバックの保持

- RSI-Anythingを参考に、経験の記録と次のループで有効な知見として使うことを区別する。すべての経験をそのまま引き継ぐのではなく、有意義なフィードバックを選別する。
- 有効なフィードバックは該当ディレクトリの `README.md` に一覧を示し、次ターンのコーディングエージェントへ渡す。エージェントが作業中に必要な方針へ反映する。
- 却下したフィードバックは削除せず `rejected_feedbacks` に残し、エージェントから読み書きできない領域に分ける。reject操作はMCPコマンドで行う方向とする。
- フィードバックの種類分けと、rolloutを表示・非表示にする判断は別の論点として扱う。
- RSI-Anythingでの選別の仕組みは参考にするが、数学問題用の選別基準や具体的な手続きは別途設計する。参照: [RSI-Anything論文](https://arxiv.org/html/2610.13912v1)

## 開発用MCPの参考資料

開発用MCPの構成例は `docs/手順/centers/docker-center/docker-center対応方法.md` の「dev_mcp（開発用MCP）の例」にある。例では、MCPごとに `dev_mcp/<mcp名>/` を設け、`compose.yml`、`.env.example`、`prepare.sh`、`setup.sh`、`.python-version`、`pyproject.toml`、`uv.lock`、`server.py`、`docker/Dockerfile` を配置する。

Docker Composeからリポジトリをコンテナ内の `/workspace` に読み取り専用でマウントし、uvのキャッシュ・仮想環境・管理Pythonは `_cache/` にマウントする。ホスト側の `prepare.sh` で保存先を作り、起動時の `setup.sh` で `uv python install --no-bin`、`uv sync --locked` を行ってFastMCPサーバーを起動する。FastMCPはHTTP transportを使い、コンテナ内の `0.0.0.0` と環境変数で指定するポートを待ち受ける。

同資料のパス例はリポジトリ直下の `dev_mcp/<mcp名>/` を前提にしている。今回のテンプレート配置では `templates/dev_mcp/workflow_mcp/` が原本となり、コピー後は `project/dev_mcp/workflow_mcp/` となるため、Composeのビルドコンテキスト、作業ディレクトリ、マウント、起動スクリプトのパスをこの配置に合わせて設計する。
